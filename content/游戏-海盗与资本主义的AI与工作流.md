这篇文章阅读大约需要14分钟。

本文讲的是我一个人制作独立游戏《海盗与资本主义》时，怎样和AI协作。这款游戏用Unity制作，代码仓库的代号是Warship，游戏本身讲的是什么，我放在了另一篇文章[《海盗与资本主义》的玩法设计](游戏-海盗与资本主义的玩法设计.html)里。游戏的代码绝大部分是Claude Code在我的指导下写的，它也负责起草、维护项目里的文档，并驱动Unity编辑器做验证；一部分正式美术由ChatGPT/Codex作为“美术代理”交付；我负责设计意图、拍板和验收。文中凡是AI做的东西，我都会注明，包括几张由Claude拼合的对比图。这篇文章我将依次讲到分工、文档、验证、美术与音效、踩过的坑，以及结尾的一些数字。

## 一个人和两个AI的分工

确切地说，这个项目的参与者有三方，即我、Claude Code，以及作为美术代理的ChatGPT/Codex，各自负责的事情如下：

| 参与者 | 负责的事 |
| --- | --- |
| 我 | 设计意图和拍板；否决方案；试玩验收；听音效、打分；需要人来判断的选择（比如保存还是不保存场景） |
| Claude Code | 写代码；起草并维护设计文档、功能计划书和CLAUDE.md；通过Unity CLI编译、跑测试、截图验证 |
| 美术代理 | 由ChatGPT/Codex担任；按规则只交付美术（图片，以及美术规范里家具一节的文字），不改代码和玩法数据 |

我这一部分具体做什么呢，其实就是提出设计、拍板和否决，下面举三个例子。第一个是榴弹炮的弹道，10月7日11:45的提交里，榴弹先做成了“飞行中修正方向”，17分钟后改成炮弹不拐弯、船员按目标船当前的速度预判，文档里记着那一版“用户否决了”，这里的“用户”就是我。制导留给了将来的导弹，不过第一版制导导弹当天中午就进了代码，和这条设计还没有统一。第二个是撞击断裂，同一天从下午到晚上前后改了五版，规则最后定成“不丢格子（玩家定）”，验收标准是各种撞法之下“格子总数一个不少”。第三个是控制台，10月7日我说“暂时我不想更新控制台了 但是保留他”（原话照录，错别字也是我的），于是现有的控制台命令原样保留，新功能不再往里加命令。我想，AI把“做一版来试”的成本压得很低，所以我的精力可以放在试玩和否决上。

美术代理的边界划得更严格一些。美术管线的说明文档里有一段复制给ChatGPT的交付说明，要求它不改`Assets/Scripts`、`Assets/Data`、`Assets/Editor`和文档，不运行`git`，不新建任何工具脚本；新图如果需要改占格、射速、挂点，要“写在回复里告诉用户”，由我和Claude去改；“如果你觉得还应该顺手改别的……先问”。CLAUDE.md里有对应的英文规则，意思是美术代理只交付美术，玩法数据和代码由Claude在我同意后修改。我想这样分有两个好处：一是占格、射速本身是设计决定，应该从我这里出，而不是在换图时被顺手改掉；二是每一类改动只有一个AI负责，就不会互相覆盖，出了问题也容易追溯。

从提交记录上看，仓库里192个提交的作者都是我，其中189个带有Claude的共同作者署名，这只能说明这些提交是和Claude Code一起完成的，并不能说明哪一行是谁写的。我不逐行写代码，但是设计由我来定，验收也由我来做。

## 用文档做AI的长期记忆

AI为什么需要文档呢，因为它记不住上一次对话。10月2日22:24，仓库里新建了`Docs/玩法设计/`目录，提交说明写的理由是，设计意图此前“只存在于对话和助手的本地记忆里”（原文是“it only lived in conversation and in the assistant's local memory”）。同一个提交还把维护文档定成了Claude的义务：对话里一旦定下设计，同一轮就要回写到对应的文档，并在变更记录里加一行。各份文档的分工如下：

| 文档 | 回答什么，以谁为准 |
| --- | --- |
| 玩法设计 | 想要什么玩法、为什么、哪些没想清楚；以我的话为准（中文，写给我） |
| 功能计划书 | 代码现在做到了什么、还缺什么；以代码为准 |
| 架构计划书 | 代码怎么组织、有哪些技术债；以代码为准 |
| 待解决细节 | 已经发现但暂时不处理的问题，只记我说要记的 |
| CLAUDE.md | 写给Claude的工作规则和踩坑记录（英文） |

`Docs/玩法设计/`的README里的原话是：“设计文档写‘想要什么’，功能计划书写‘做到了什么’。两者不一致的地方，就是接下来要做的事，或者是需要重新讨论的设计。”另外，代码里一个TODO都没有，已知但暂时不修的问题都记在待解决细节里，比如敌船AI那一节写着“只记载，不修”，注明是我在10月7日定的。设计也常常先落进文档：10月3日凌晨00:04到00:27的五个提交全是文档，没改一行代码；全部提交里有48个只改了文档，改过`.cs`文件的109个提交里，约90个同时改了文档或CLAUDE.md。

维护规则的第一条是“你说了算”，也就是以我的话为唯一依据，不确定的地方标成未决问题，不替我做选择。功能做完后，状态标记从“已商定未实现”改成“已实现”，实现细节写进功能计划书，不写进设计文档。另一条是每条规则都要带“为什么”，原话是“只写‘是什么’，过几个月会忘了当初为什么这样定”，这和我在[我的游戏玩法设计理念](游戏-游戏玩法设计理念.html)里说的“对于任何一个设计决定，都要说出这样设计的理由”是一个意思。理由还会被后来的系统继承，以命名为例，实体名和资产名一律不许带空格，最初是因为控制台按空格分词；后来存档按名字找回资产，这条规则又成了存档的硬约束。

这些设计文档是Claude以“我”的口吻写给“你”，也就是写给我的。README开头写着“由你决定方向，由我起草、整理、实现后回写状态”，状态栏里写着“草稿，请你核对”（读起来很像一份工作汇报）。Claude实现时自己定的默认值会单独标出“请你确认或改”，比如小队的指挥半径默认10格；我拍板的地方标“玩家定”。

功能计划书以代码为准，但是写的时候也会出错。Claude在战斗文档的变更记录里自己更正过，“武器自动索敌和瞄准其实已经实现，之前写成‘没做’是错的（没读代码就写了）”，同一个提交也改了功能计划书的正文。其实功能计划书从8月16日的第一版起就写着“修改前请先与最新代码核对”，那次写错，正是因为没有照这条提醒去做。

CLAUDE.md放在仓库根目录，是写给Claude的工作规则。8月16日的第一版约2.6KB，只有两节规则：回复用中文，游戏内命令走控制台；到10月9日已经长到约61.7KB，前后33个提交改过它，增加的内容大多是踩坑记录。语言按读者来分：CLAUDE.md用英文，设计文档用中文，代码用英文；玩家看到的文字按规则一律走`Loc.T`（上帝之手调试面板是我定的例外，右键命令菜单里也还有写死的中文没改过来），中英两份语言表各512个键同步维护，尽管游戏里还没有切换语言的入口。CLAUDE.md的原话是“the inconsistency is the correct choice, audience-driven”，意思是这种不统一是按读者做出的正确选择。

但是规则写进文档之后，AI仍然可能漏看，如果写成测试，漏掉一处测试就会失败，因此容易漏的步骤都写成了测试：新增一项船员技能要改十来处，`EveryListedFieldName`会抓出漏掉的读写分支；按键表和枚举的顺序必须一致，由`ActionTableIsIndexedByEnumValue`检查；新的静态状态必须登记进读档时的清空流程，漏登记的话，也有一个专门的测试会失败。

## 让AI自己操作Unity编辑器

Unity是图形界面程序，AI默认看不到画面，也点不了按钮，要让它自己验证，先得让它能操作编辑器。早期是通过`unity-mcp`中继驱动编辑器，10月2日换成了Unity CLI：项目里装`com.unity.pipeline`包，它在编辑器里开一个只监听本机的服务，Claude从命令行用`unity command ...`调用。按CLAUDE.md的说法，换掉的原因是Unity已经弃用了那个中继。

标准循环是这样的：先批量修改；然后跑`compile-check.ps1`，一次调用完成健康检查、导入、编译和短超时轮询，只打印不重复的错误行，约10到20秒；再跑`run-tests.ps1`，场景有未保存的改动时它拒绝运行，EditMode约9秒，PlayMode约21秒；接着用`eval`或`eval_file`在运行中的游戏里执行C#、读取状态；最后用`capture_game_view`截图，再由Claude读这张PNG。`Tools/unity-editor`下这类脚本共8个、约500行，也是在和Claude的协作中写成的。

这套流程里有两条规则是我定的：一是截图一律用1920×1080，因为停靠的Game面板在这台机器上是885×873，截出来被拉伸，和玩家看到的不一样；二是开发期可以随便进出Play模式、跑PlayMode测试，不用先问我，理由是“没有需要保护的游玩过程”。

测试也是分层的，先要问的是，这个检查需要长期保留，还是只查一次：只查一次的在Play模式里用`eval`查，容易复发的才写成EditMode或PlayMode测试；早期的“AI自测”这一层8月就已冻结，10月7日删除。测试和工具不碰我的真实数据，改键、存档、音效评分都有指向副本的测试接口（`SetStoreForTests`、`SetRootForTests`）。CLAUDE.md还提醒，测试通过只证明它断言的东西，冒烟测试就只断言了`1+1==2`。

规则本身也要用实验验证。命中规则是“体积就是命中率”（体积是船员的体型属性，子弹飞到他身上时按这个概率命中），Claude在Play模式下向体积0.8的船员打了300发，命中234发，也就是78%。`battle_setup.cs`会搭一场每边10名船员的镜像对战，`battle_report.cs`输出每艘船的快照，一场80秒的对战帧时间约2.5ms。`measure-frame.ps1`测得6团毒气每帧约多0.7ms，6处地板火约多2.6ms，所以火苗数量要压低。

当然，也有一些办法行不通。`simulate_key`会返回“Success: true”，键盘状态却一动不动，CLAUDE.md于是写下“don't spend time on them again”，意思是别再在它们身上花时间。替代办法是调用按钮背后同一个公共方法：建造界面的Depart按钮调的`SwitchToPlayMode`，只是对控制台`mode p`那个处理函数包了一层，CLAUDE.md称之为一条代码路径、两个入口；验证时在`eval`里直接调用这个方法，效果和点按钮一样。另外两种办法是用`InputSystem.QueueStateEvent`注入按键，或写带虚拟设备的PlayMode测试。但是撞击、残骸、敌船AI这类讲手感的系统，这些办法都验证不了，还是要靠我进游戏看。

10月5日我放宽了规则，合适的地方可以用代码画扁平矢量图，游戏里的船员就是这样画的：衣服表示身份和装备，脸用来认人，手表示在做什么。Claude也用Python脚本画过一些平面占位，比如导弹发射架。

Blender程序化建模是中间的一个阶段（`Tools/art_blender`）：用`bpy`写代码建模，正交俯视渲染，1个Blender单位等于1格，+Y是船头，光从左上方来；后处理加描边和不带方向的接触阴影，因为图层在游戏里会旋转，不能烘焙有方向的影子；最后4倍降采样，得到每格256像素的图。第一把正式机枪的三层就是这样做的，10月8日被替换，它已经不是现在的主要管线。

美术代理这边分三步。第一步是规范，出图按`Docs/美术规范.md`，里面直接附了给AI出图的英文提示词和避免项，比如透视、等距视角；我否决过一版武器概念图的配色，之后以选定的机枪和八号榴弹炮为参考，钢灰炮体，灰绿支架。第二步是交付，每个图层单独一张透明PNG，俯视，船头朝上，原图和交付单放在仓库外的`gpt_inbox`；会转动的零件要量出原图上的回转中心，写成`anchor`。

第三步是处理，用Claude写的Python工具`art_pipeline`，先`analyze`再`process`，裁掉透明边，缩放进“格数×每格像素”的画布，把锚点对到轴心，并检查内容碰边、背景没抠干净、边缘发糊、原图太小被放大这几类问题，有问题时退出码为1，警告为空才算完成。所有数字都从命令行或交付单传入，不为某一件物品写死。已接进游戏的有美术代理画的1×2、2×3、2×4喷气引擎（提交说明里写着art by Codex）、八号榴弹炮和留声机，床、医疗床和部分家具也换成了正式美术，其中三件换图前后的对比如下图所示：

![占位换成正式美术前后：左边是引擎，从“机”字色块换成Codex画的喷气引擎；中间是榴弹炮，从旧占位换成八号榴弹炮；右边是床，从旧的1×1换成新的1×2](求职相关/游戏/海盗与资本主义的AI与工作流/before-after.png)

音效也是同样的分工。占位音效是Claude用代码合成的WAV文件，比如哀嚎是带颤音、音高下滑的锯齿波。第三方音效素材库放在仓库外，因为Unity商店的许可协议和各素材包的授权不允许把原文件提交到公开仓库。我在试听页给音效打星，共标注了136个，来自Sonniss GDC 2024音效包和Unity商店的7个包，再到游戏里的Sound Lab边玩边评分，Claude读评分文件，把选中的接进游戏。现在武器开火和装弹是真实录音，界面和放置的声音是我在Sound Lab里挑的，命中、哀嚎、爆炸等仍是占位。

## 踩过的坑

下面这些坑大多写进了CLAUDE.md，每一条都带着原因。其中多数是在10月2日那批提交里第一次记下来的，所以下面不写具体日期。

<div class="list-flush" markdown="1">

1. 验证，不要只推理。引擎尾焰的方向在一次会话里来回翻了三次。原因是粒子系统的锥形发射器永远沿自身的局部+Z发射，而用`Quaternion.Euler`绕X轴转90°，再乘以`Vector3.forward`，得到的是-Y，符号和多数人第一次的猜测相反，CLAUDE.md自嘲说这个项目也猜错了，而且错了两次。现在规定方向要在`eval`里算出来，或者读出正在发射的粒子、转到世界坐标再下结论。船头是+Y这件事，也是让物理真正跑起来确认的。
2. 用同一个公式自检，只能证明自洽。`GridToWorld`把半格偏移直接加在世界坐标上，没有跟着船旋转，船转到约345°时偏差约0.18个单位。它藏了很久，因为所有自检都是拿同一个公式和它自己比，两边错得一模一样，当然对得上。直到用Unity自带的`Grid.GetCellCenterWorld`作独立参照，问题才暴露。
3. 采样真正被读取的那个值。船在推力下会抖，云层也跟着抖，根因是`Rigidbody2D`没开插值：物理50Hz，编辑器里渲染约480fps，同一个位置连续画2到6帧再跳一步。诊断时要逐帧采样`Transform.position`，而不是`Rigidbody2D.position`，后者始终是原始的模拟值，开不开插值都一样，看不出问题。云层本身没有bug，它只是镜头位置的函数。
4. 不要写静默回退。缺资产、缺文件、加载失败都要立刻、明显地报错。例如船体贴图加载失败就直接抛异常，不偷偷画一个纯色方块顶上；音效文件缺失也直接抛异常。CLAUDE.md给的理由是，让问题在发生的地方暴露，而不是在下游变成一个让人困惑的症状。
5. 模态对话框会卡住整个命令队列。场景有未保存的改动时跑测试，会弹出“场景已更改”的对话框，之后所有命令都超时。诊断用`editor-doctor.ps1 -Windows`列出窗口标题；保存还是不保存由我决定，AI不替我点。预防有两条。一是`open-editor.ps1`只自动回答已知无害的“Recovering Scene Backups”，按“否”，因为所有工作都在代码和Git里；遇到不认识的对话框不要猜，列给我看，我说过怎么按之后才加进自动作答表。二是`run-tests.ps1`遇到未保存的场景直接拒绝运行。这个检查刚写好就有bug：返回的JSON回显了提交的源码，源码里本来就有“DIRTY”这个词，于是场景永远被判定为有改动。
6. 减少无谓的等待。有一次请求花了24分钟，其中约70%在等待，于是定下时间规则：编译、轮询、读取不塞进一个长超时命令。Unity窗口在后台时不会自己编译，新脚本放了37秒都没动，但从后台调用`recompile`是可以的；把窗口切到前台当成常规步骤是个错误，多耗了约4分钟。

</div>

我想，这些坑大多不是AI独有的，人也会犯，但是AI给出的解释总是很流畅，报告“完成”也很快，因此我更愿意相信独立参照和实测的结果。

CLAUDE.md里的规则大多是踩坑之后加进去的，比如大地图海图的第一版，在面板还没完成布局、`_scale = 0`时进入了死循环，耗尽内存，导致编辑器崩溃，于是CLAUDE.md里又多了一条：由界面尺寸推出来的数值，在循环之前要先检查是不是有限值。
