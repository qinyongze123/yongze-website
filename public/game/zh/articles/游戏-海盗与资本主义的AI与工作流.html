《海盗与资本主义》的AI与工作流

这篇文章阅读大约需要15分钟。

本文讲述我在制作独立游戏《海盗与资本主义》的过程中，我如何辅助Claude Code进行游戏开发，以及我构建了怎样的工作流来加速开发。我会先从我和AI的缘分说起，然后介绍我使用Claude Code的方式，最后按照工作内容列举我的工作流，包括图片生成、物品和小人管理、音频管理、性能分析、世界经济系统原型开发等方面。

前因后果，我与AI

这一章讲述我视角下AI发展到2026年10月17日的样子。这一章在今天看本身就很有趣，十年后看会更加有趣。

上大学的时候我就有做独立游戏的打算，当时我装了Unity，断断续续地学习Unity的C#编程。但我的拖延症加上枯燥的学习过程，让我对游戏开发总是浅尝辄止。2022年11月，ChatGPT 3.5问世。当时我放假在家，通过OpenAI的网站第一次使用了能和人对话的AI产品，我感到一阵眩晕，犹如亲眼目睹了原子弹的爆炸，心里默默浮现出四个字：“未来已至”。

那个假期里，我开始用AI制作自动回帖机器人，捉弄百度贴吧的吧友。我注册了四个ChatGPT账号作为请求池，用Selenium搭建了一个AI自动回帖工具。当时ChatGPT 3.5的模型能力不够，我的回帖机器人又没有识图功能，回复的内容经常驴唇不对马嘴。但是当时AI的概念刚刚在中国兴起，大家并没有防范心理，没有一个人发现我的贴吧账号是AI回帖的，我因此总能引起一波又一波的骂战。

后来，新的AI模型和新的产品井喷式涌现。2025年我在使用Cursor辅助编程，它是那个时代典型的AI辅助编程产品：中间是一个代码窗口，供开发者查看代码，右侧是另一个窗口，供开发者和AI对话。依靠这种形式，它实现了AI修改代码以及代码自动补全的功能。

之后，GitHub Copilot发放了一年的学生订阅，我领取后开始使用Copilot。2026年初，我发现Claude的模型更强，就改用Claude Code CLI。当时Anthropic认为命令行就是一切，因此大力推行基于命令行操作的AI产品。与此前的产品相比，另一个不同在于Claude Code的VS Code扩展不主张提供代码修改记录，也就是说，Anthropic认为他们的AI所做的代码修改已经不需要人工审查了。2026年夏天，我开始使用Claude Code CLI结合Unity MCP做游戏开发。直到2026年九月，我才发现Claude Code桌面端有更清晰的界面和强大的内置浏览器操作能力，于是开始使用桌面端。

Claude Code桌面端和Codex类似，已经彻底变成了一台“许愿机器”：它只保留会话记录和会话管理界面，彻底抛弃了代码的显示，也就是说开发者只使用自然语言编程，不再触碰程序代码（不久的未来，代码终将变得像汇编一样小众）。而2026年九月GPT-6 Astra和Claude Opus 5.5上线之后，AI coding领域变成了Anthropic和OpenAI的决斗，模型的能力又上了一个新台阶，这无疑是又一颗原子弹的爆炸。我在想：“属于独立游戏设计师的时代终于到来了。”

现实世界是割裂的，而我是孤独的。很多公司的面试依旧考贪心算法、动态规划，我周围的一切也都是安宁的样子，仿佛整个城市和所有的人都与十年前没有区别。但是在互联网上，尤其是在X上，AI的消息漫天飞舞，地动山摇。每一周都有翻天覆地的变化，在AI的辅助下，开发者的生产力急剧提升，如今一个月就能完成过去一年甚至几年的工作量，这让人不由得想加把劲，让工作再快一点。

一方面，我很高兴自己能成为时代发展的亲历者，看到新技术的崛起以及它对人类社会的改造；另一方面，我又感到彷徨，因为我并不很适应这样的发展速度。我的猿猴大脑，从进化的角度看，最初的目的也许是预测环境的变化：我的祖先用这个大脑规划动作、预测天气、记录地图。而今天，我却尝试用同一个大脑预测未来十年的行业发展，来给自己做职业规划。悲哀的是，我完全无法预测任何事情，在这个时代也没有人能够准确预测任何事情，更重大的变化随时可能在不久的未来出现。在这种巨大的不确定感之下，我感到强烈的不安。与此同时，这个社会又是如此冰冷：如果一个人没有钱，就没有食物和住所。在这样的情境下，我居然有点理解那些原始主义者和“阿米什人”了。

整体工作流

这一章讲述我用AI开发《海盗与资本主义》时的整体工作流。

我用Claude Code以及各种工具进行游戏开发。在Claude Code中，我用很多会话分别推进不同的任务。每个会话都是一个AI智能体，相当于我手下的一名员工：它们有各自的记忆，可以创建子智能体，可以并行运行、互相发消息、调用各种工具。大多数会话使用Opus 5.5模型，effort（推理强度）视情况而定，在medium和ultracode之间。我的会话大致如下：

会话 职责
warship all 与我讨论整体项目，协调各个会话，整合结果
warship perf 做性能分析与性能优化
warship art 负责美术工作
warship audio 负责音频工作
map gen and clouds 负责远处背景的地形程序化生成
pawn lab 负责游戏小人（pawn）形象的程序化生成
capitalism 负责游戏世界经济模拟系统的开发与调试

以上是多AI会话并行的工作方式。warship是我早期使用的游戏代号。

Claude Code自带很多内部工具，包括联网搜索、操作电脑文件、操作内部浏览器等。除此之外，我使用的外部工具有：

工具 用途
Unity CLI Unity推出的新一代AI扩展，用于AI开发Unity游戏，取代了之前的Unity MCP
Blender MCP 让AI直接在Blender中建模和摆放场景
gpt image bridge 自创的图像生成skill，允许Claude Code调用我的Codex CLI生成图片

总的来说，现在的AI能力完全足够独当一面，但是和AI合作时仍然有很多注意事项。按照我的经验，主要有以下几个问题：

  1. AI的记忆能力（上下文）是有限的，所以AI擅长专注于单一任务，不擅长综合与管理。

  2. AI的信息检索和实践能力强，但创新能力一般，所以AI擅长做项目复现，不擅长研发全新的算法。

  3. AI能独立完成的任务是有限的：普通任务可以靠AI长时间自我迭代解决，少数特殊任务必须依靠人工干预。

  4. AI的任务耗时是个问题。做开发消耗的token不是问题，但是任务耗时太长会影响开发节奏。

针对这些问题，我在开发时有以下几个技巧：

  1. 在我有大块时间的时候，我主导AI开发那些最需要创意和综合能力的工作，例如游戏的玩法设计。此时AI的主要职责是辅助我头脑风暴，帮我检索和整理信息、辅助我判断（例如做竞品分析）。在我只有碎片化时间的时候，我监督AI完成它比较擅长的工作，例如监督美术素材的生产、修改SVG图片等。这个过程中AI可以半自动完成工作，但仍然需要人工干预。在我不在的时候（吃饭、睡觉、休息），AI全自动完成它擅长的工作，包括性能测试与优化、成熟系统的参数调整等。此过程中AI完全可以自主编程和测试，只有极少数情况需要我介入并做出决定，例如是否需要做一个转场动画来遮盖场景更换的痕迹。

  2. 在AI做那些我并不放心的任务时，或者AI已经在某个任务上浪费大量时间时，可以让AI先生成一份方案，我通过方案检查整个环节是否有可以优化的地方。例如做“世界经济模拟系统”时，AI最开始开发缓慢，我提出了一些建议，包括“从小规模开始做模拟，先观察量与量之间的因果关系，再放大到目标规模”，以及“在电脑的16个物理核上同时跑，一次收集多组实验数据”，这帮助AI大大加快了开发进度。

  3. 做复杂的新任务之前，先让AI调研现有领域内的最新进展。AI的知识储备虽然渊博，但很多时候缺乏足够的发散能力和常识。让AI查找并复现SOTA（当前最先进水平）的项目，可以让它快速追上该领域的最先进水平。

  4. AI很容易被误导，因此在发送消息或者参考图片时，不要提供错误的信息或示例，应该清晰明了地直接描述任务，以及正确的结果应该是什么样子。

2D美术资源生成途径

现有的2D图片创作工作流大致有：着色器、SVG矢量图、GPT Image 2.5、Blender建模渲染。（这部分并没有涵盖世界模型以及Midjourney等。）

它们各有特点：SVG和GPT Image 2.5生成速度比较快，着色器和Blender相对更慢，其中着色器需要反复迭代，Blender需要先建模再渲染。

以下是效果展示：我让这四种方法在同样的agent配置和同样的要求下，各生成了一张图片。

着色器
直接用代码绘制一个图像。
特点：Claude Code原生的生图方式，需要迭代，画面还可以。
SVG
矢量图，本质是一段描述形状的文字，所以AI写起来最顺手，人也能直接改里面的数字和颜色。
特点：适合做现代扁平风格，方便人手动修改，不擅长复杂画面和写实画风。
GPT Image 2.5
OpenAI的图像生成模型，用文字描述直接出一张图。
特点：有极佳的生成质量，但是风格控制和视角控制很困难。
Blender建模渲染
让AI用Blender的脚本建出三维模型，再从正上方渲染成图。
特点：擅长硬表面，很不擅长软体雕塑，很容易约束形状、控制视角。

一个实用的方法是：先用Blender或者SVG做粗糙但容易控制结构和视角的草图，再把草图作为参考交给GPT Image 2.5进行图生图。这让我不禁想到了一张关于DLSS的梗图：

《海盗与资本主义》是一个以俯视角为主的2D游戏，因此需要的美术资源大致如下：

  • 船体和物品：固定大小的、纯俯视角的、分图层的图片素材。
  • 游戏内的小人：程序化生成正面、侧面、背面的小人，尺寸和位置需要严格统一。
  • 世界远景：需要无限生成的、地形多样的、纯俯视角的世界远景。

因此，我为每一类素材选择了不同的生成方法：

素材 用什么方法生成 为什么
船体和物品 先用GPT Image生成概念图，放到Art Lab中人工审核，再用GPT Image拆成图层，最后进行标准化 首先生成纯俯视角概念图，确认视角正确、设计美观之后再拆解图层。标准化可以移除接近透明的颜色，并控制中心和大小
小人 用GPT Image生成多图层的参考图，由Opus结合脚本转成矢量图，最后在Pawn Lab中拼装与审核 要求正面、侧面、背面三个视图，大小严格统一，颜色可更换，矢量图最方便修改
远景 程序化生成远处的地形和云 需要无限生成清晰、连续的地形

物品生成与管理

我做了一个叫“美术工作台”（Art Lab）的工具网页，用来查看与管理游戏内的物品美术素材。

美术工作台管理着所有的游戏内美术资源，以及开发过程中的美术草图。一件物品的美术资源要顺利进入游戏，需要经历三个阶段：概念图（整件东西长什么样）、分解图（拆成图层之后对不对）、游戏效果（真的放进游戏里好不好看）。只有通过三个阶段的物品才算定稿，定稿后的物品还会有自己的交付单，包含星级与备注。美术工作台的一个功能，就是把每件物品每一步生成的图片、我的请求、AI的回复、自动检查的结果、标准化后的结果、我的最终打分与备注，都整理到同一张卡片里。这样我可以方便地调整任何美术资源，也可以替换掉之前并不满意的素材。美术工作台的界面如下图所示：

Pawn Lab

在介绍Pawn Lab之前，我需要先说明一下游戏内的小人生成。小人就是pawn，指游戏内的人类形象。为了程序化生成风格相同、形象不同、三视图统一的小人，并实现小人更换装备和衣物时的形象变化，我采用了类似《环世界》和《监狱建筑师》的矢量图小人绘制方式。具体来说，每个小人都由多个矢量图堆叠而成：最底层是头颅和躯干，然后叠加第一层上衣和裤子、眉毛、眼睛和头发，再叠加第二层衣物和配件。在此基础上，只要制作一件新衣物的正面、侧面、背面视图，并规定其图层叠放顺序，就可以为小人增添一件新的可选衣物。以下动画演示了小人形象的生成过程：

由于要大量地检查和编辑小人的服装、发型、五官等的生成效果，我制作了一个名为Pawn Lab的小人工作台。Pawn Lab是我自制的网页端矢量图编辑工具（是的，你没有听错，我的确在维护一个在线矢量图编辑工具）。它的矢量图编辑功能与我用过的Inkscape、Affinity比较相似，但新增了很多本项目专用的功能：小人物品装配面板、现有物品检查面板，以及对正面、侧面、背面三个视图下矢量图编辑的支持等。我用它检查并修改AI生成的SVG美术资源。

音频工作流

我做了两层音频工作台。第一层是一个本地的音频试听网页，我可以把外部的音频资源导入这个网页，一个个试听，给它们打星，标注将来的用途。下图是音频试听页：

被音频试听页标记的音频会被当作备选的游戏音效，送入第二层音频工作台“Sound Lab”。这是一个集成在Unity Editor游戏内的音频试听工作台，通过内置的控制台代码呼出。我把每个要测试的游戏事件当作一个槽位（比如“放置物品”槽位、“按钮按下”槽位），Sound Lab可以让槽位触发我在其中选中的备选音效。因此我可以选中一个音效，在游戏中触发真实的事件（例如放置一个物品），并听出这个音效用在这个事件上是否合适。Sound Lab还提供简易的开头剪裁、音量平衡、屏蔽其他声音等实用功能。以下是Sound Lab在游戏内的界面：

性能分析工作流

我和AI构建了名为“perf”的游戏内性能分析工具，可以通过控制台打开，界面如下图所示。这个工具会显示一秒内的平均帧数、十秒内的最慢帧，以及各种耗时构成。

用这个图作为例子，可以看到最近十秒内有三帧超过了33 ms，最慢的一帧发生在7.4秒前，耗时43.3 ms，又可以拆分为“脚本35.1 ms + 物理0.0 ms + 渲染和界面6.3 ms + 其他1.9 ms”。

该工具还显示当前帧中主线程、GPU、物理、脚本、渲染各自的耗时，以及游戏内的船只碰撞耗时和世界经济系统解算耗时。

我一般在Unity Editor内游玩，perf工具可以帮我寻找卡顿的成因。然而考虑到真实打包后的游戏通常表现更好，我使用warship perf会话来测试真实游玩帧率并进行优化。

这个会话会先打包出正式包，然后让游戏在后台自己回放固定的场景（10对10或30对30的混战、两船相撞、高速飞行、刚启动等），记录最慢的1%帧、最慢的一帧、超过16.7毫秒的帧位置，再加上撞击、选目标等环节的单独计时和垃圾回收的次数。

找到卡顿发生的位置之后，warship perf会用带分析器的dev包重新播放同一个场景，定位到卡顿帧，按每个函数的耗时排序，从最费时的开始往下拆解。常见的原因是重复计算、每帧新建大数组、一艘船断开时所有船都在重新计算等。每次只改动一处。凡是能做到“结果完全一样”的优化，就保留旧算法，逐条与旧算法的结果对拍。单元测试全部通过、在编辑器中运行一遍、再在打包版上对比之后，它会把数字写进提交说明。

世界经济系统开发工作流

我给游戏世界开发了一套动态的世界经济系统，对生产、消费、贸易等经济行为做了真实模拟。我追求依靠系统自身的负反馈调节来实现我想要的稳态，依靠价格差吸引商船出现，而不凭空生成任何单位，因此这个开发过程相当艰难。

为了高效地进行经济系统的原型开发与测试，我没有一开始就依赖Unity，而是让AI用JavaScript写了一个网页原型，里面有城镇、商船、海盗、军队、战争和货币。整个开发和调试都由capitalism会话负责，全部调试好之后，Unity再把它当作一个子进程来请求数据。

为了方便我审查，这个原型有一个完整的界面，如下图所示。在其中可以直接看到整个系统的运行：城市、势力范围、船和风向、空中障碍物，右边是总人口、货币总量、商船、海盗、军队的数量等参数。

在这个世界经济系统的原型开发过程中，我逐渐梳理出了一套与capitalism会话协作的工作流：我只提供方向和要求，不提供具体数字上的约束。我要求这个系统让玩家能够识别经济的运转方式，因此玩家需要能从中读出航道、价差、巡逻和战争的周期。我用以下指标衡量世界的好坏：商路是否稳定、价格差距是否稳定、三种船（商船、海盗、军队）的数量是否稳定、动态平衡是否难以打破。我明确禁止系统强行固定数量，稳定只能来自收益的负反馈，不准人为加奖励或噪声。

capitalism会话负责把这些要求变成可测量的数值指标，并用指标观察世界是否符合要求。它搭了一个实验环境，允许同时跑多个随机种子。由于这个世界要跑几十年才能稳定，它总是忽略世界成长期的波动，从稳定状态之后开始观察。遇到问题时，它不会强制规定数量，而是去查看：为什么收益没有吸引新的投机者加入，系统内的单位把时间用在了什么地方，整个系统的金钱流向了什么地方。每个改动都从假设出发，尝试几个不同的取值，不光看期望改善的那项指标，也看别的指标有没有被拖累；选定之后让世界重新跑到稳定，再用热力图确认规律可见。做完后，实验数据写进提交记录，踩过的坑写进说明文档，设计上的决定写进玩法文档。
