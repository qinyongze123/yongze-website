I use Claude Code heavily almost every day. It has become fully woven into my life, helping me build web pages, look up information and develop all kinds of projects. Recently I have been using its official browser extension "Claude in Chrome" as well as Unity MCP, and I gradually noticed that Claude Code's response time was causing problems in my workflow. For example, sometimes I give it a task and it takes 20 minutes, even half an hour, to finish. That execution time alone limits my daily productivity to a large degree. On top of that, I suspected something was wrong with the Claude in Chrome extension, because even simply opening a web page with it takes ten-odd seconds, sometimes tens of seconds. There are many ways to cut the time a task takes: choosing a lower effort level, using prompts, or having it use other MCP tools, and so on. But before any of that, I wanted to know what Claude Code actually does internally while executing a task, so that I could see where the time really goes and then optimize how I use it from my side.

Against this background I built a local monitoring tool for Claude Code, which I call Claude Spy — as the name suggests, it "spies" on Claude. It tallies, for every request in every session, the steps Claude Code performed and how long each took, and shows them visually as a local web page.

## How It Works
The initial approach was to use the official telemetry interface that Claude Code provides. Claude Code itself speaks the OpenTelemetry protocol and reports runtime metrics and logs to an external collector. I used this interface to connect Prometheus and Grafana, and that toolchain can capture token consumption, cost, working time, tool calls and so on. However, the officially reported data is only precise down to the level of a "tool call" or a "single request"; it contains no statistics about the specific internal thinking steps and their durations. So I started looking for other solutions and turned to parsing the local session files myself, which led to this tool.

Claude Code records every session locally as a jsonl file under the `~/.claude/projects` directory. Each line is an event: a user request, the model's thinking, a tool call, and so on, together with a timestamp accurate to the millisecond. This data can therefore be collected for statistical analysis. The catch is that this format is designed for Claude Code's own CLI, so it is full of edge cases; for instance, pasting an image inserts an accompanying message.

Claude Spy reads these session record files and parses out the boundaries of each request; each request is then split into several smaller events: thinking content, reply content, tool calls and so on. The backend is a small server written in pure Python standard library, with no third-party dependencies installed, and it exposes only two read-only endpoints: one that lists all local session files, and one that parses a given session and returns structured results. The frontend visualizes the data, using SVG to draw, for each round of requests, a bar chart broken down by event category. The vertical axis of the bar chart can show the number of event calls, the average duration, and the total duration. The event categories include thinking, replies, internal tools and external (MCP) tools, each distinguished by a fixed color. Clicking a bar filters by that event type, and the timeline below automatically filters to show only events of that category. The whole of Claude Spy was itself developed with heavy help from Claude Code (eating our own dog food).

## Some Findings
Looking at the results, the first thing I noticed was that Claude Spy's event list reveals Claude Code's pattern of thinking. In the following scenario, I asked Claude Code to look at a specific file inside a folder. Claude Code finished the task in 35 seconds, with the events executed in this order: "think, view parent folder contents, think, view subfolder contents, think, reply". You can see it habitually interleaves thinking with tool calls. Thinking is usually the biggest share of the time; in this task it took 18.9 seconds, more than half. While viewing the folders, Claude Code used the bash command twice: "ls -la ~/.claude/projects/ 2>&1 | head -20", "description": "List project folders under ~/.claude/projects", and fed the output into the next round of thinking. The current Claude Spy lets me monitor only the things above, but that was already enough to excite me, and it partly explains why even a simple task can take half a minute or even a minute.

In Claude Spy I also compiled statistics for an entire session, using three metrics: the number of event requests, the total duration of events and the average duration of events, visualized as bar charts. I used my current session, in which I did web development, information lookups and article editing, and the statistics are below. They show that thinking and replying take up a considerable share of the time. Claude's internal tools such as read, write, edit and bash also have a large number of requests, but because they execute quickly they take almost no time. The MCP tool Claude in Chrome averages around 6 seconds per request, and the "mcp__claude-in-chrome__computer" item takes up quite a lot of time (this tool is the part of the "Claude in Chrome" extension responsible for browser operations: taking screenshots, clicking, typing, scrolling and other actions that simulate the mouse and keyboard. These are relatively "heavy" operations by nature, so a longer time per call makes sense). The result itself suggests that Claude Code's own execution time has more to do with its chain of thought than with external tools, and there is not much room for optimization.
